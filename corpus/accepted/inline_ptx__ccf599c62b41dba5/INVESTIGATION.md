# Investigation: ptxas O1+ vs O0 divergence on an inline-asm block

case:      inline_ptx__ccf599c62b41dba5
strategy:  inline_ptx  (n_instr=120, n_regs32=12, n_regs64=6, n_preds=5)
config_seed: 20260810   test_seed: 9999   kernel_seed: 3970868306842774015
GPU:       NVIDIA GeForce RTX 2050 (sm_86), driver UMD 12.1

## Symptom
The exact same kernel produces:
  * -Xptxas=-O0 : matches the CPU oracle on all 128 output words, on every runnable
                  toolkit (cuda-11.3 / 11.8 / 12.1 / 12.6).
  * -Xptxas=-O1/-O2/-O3 : deterministic but DIFFERENT output (66 of 128 words differ,
                  high-byte / carry differences) on cuda-11.8 / 12.1 / 12.6.
  * cuda-11.3 stays correct at all O levels.

## Evidence that this is a real ptxas miscompilation (not testcase UB)
1. CPU oracle validated TWO independent ways: a second, hand-written interpreter of the
   same instruction sequence agrees with the generator's mirrored oracle on all 64 threads;
   the stored expected.bin matches too.
2. The unoptimized build (ptxas -O0) matches the oracle exactly -- so the oracle captures
   the true PTX semantics, and ptxas -O0 executes them faithfully.
3. Isolated to ptxas: the exact PTX emitted by `nvcc -ptx` fed directly to
   `ptxas -arch=sm_86 -O0` vs `-O1` reproduces the divergence (O0 correct, O1 wrong).
   No nvcc/cicc front-end involvement.
4. Runtime legality audit of every instruction (shift counts pre-masked, bfe/bfi
   pos/len in [0,255] with fields past the MSB well-defined, prmt selectors, immediates)
   found ZERO undefined-behaviour violations.  (Note: PTX bfe/bfi do NOT require
   pos+wid <= width; a field extending past the MSB is well-defined -- zero-extended for
   bfe, dropped for bfi.  An earlier note in this investigation claiming otherwise was
   wrong and has been removed; the generator now samples that legal over-MSB region.)
5. Root cause isolated by op-family and per-instruction disabling: the divergence is
   essential to exactly ONE instruction --
       step 37:  prmt.b32 %xr5, %xr2, %xr2, 0x6402      // prmt(d, a, a, sel)
   Disabling only this instruction (replacing it with a mov) makes all O levels agree.
   Computing the SAME prmt in an isolated kernel is correct at O0/O1/O2, so the fault is
   ptxas's context-sensitive optimization of this instruction inside the large
   (396-step) inline-asm block, not the prmt instruction itself.
6. Deterministic: 3 identical runs at every O level.

## Classification
This is a genuine differential: multiple stable builds (O1/O2/O3 on 11.8/12.1/12.6)
produce output different from the CPU oracle and from O0 builds.  The pipeline flags it
POTENTIAL_COMPILER_BUG.  Whether it is a ptxas scheduling/peephole bug or (unlikely) a
yet-unfound latent UB in the inline-asm contract is left to NVIDIA tooling; the repro
material here lets it be regenerated byte-for-byte and re-checked on any GPU/driver.
